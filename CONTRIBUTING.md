# Contributing to Taphonomy

## Current Status

Taphonomy is in early development and is not currently accepting external
contributions. It has a single author.

This document will be expanded when the project is opened to outside
contributors. Until then it records the standards that apply to all work in
this repository.

## Authorship

Taphonomy is authored by Fahad Bilal Saleem.

External contributions are not accepted. The copyright in the whole work is
held by the author. `docs/decisions/ADR-0012-outbound-licence.md` section 6
records why that matters and what would have to be in place before it could
change.

No contribution may add authorship or attribution for an automated tool. See
`CLAUDE.md` section 0.1.

## Governing Documents

All work in this repository is subject to:

| Document | Scope |
|---|---|
| `docs/SAFETY.md` | Evidence preservation and operational safety |
| `SECURITY.md` | Threat model and security requirements |
| `docs/PROJECT.md` | Project scope and non-goals |
| `docs/development/DEVELOPMENT_ENVIRONMENT.md` | Toolchain, quality gates, dependency policy |
| `CLAUDE.md` | Coding-agent operational contract |
| `docs/decisions/` | Architecture Decision Records |

Where these conflict, the safety priority order in `docs/PROJECT.md` section 7
applies.

## Quality Gates

The following must pass before any commit that changes source code:

```text
cargo fmt --all -- --check
cargo check --workspace
cargo test --workspace
cargo clippy --workspace --all-targets --all-features -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --document-private-items
```

A failing gate is not waived by the change being small.

## Evidence and Test Data

Real personal data must never be committed to this repository. This includes
disk images, recovered files, filesystem metadata, and device identifiers
derived from real evidence.

Test fixtures must be synthetic and generated by documented, reproducible
procedures.

## Commits

Commits are made manually by the author. Automated tools propose changes and
do not commit.

A commit should represent one coherent change. Commit messages describe the
change that was made, not the intent behind it.

## Dependencies

New dependencies require justification against the checklist in
`docs/development/DEVELOPMENT_ENVIRONMENT.md` section 15, and an ADR recording
the decision.

## Security

Do not report security issues through public channels. See `SECURITY.md`.
