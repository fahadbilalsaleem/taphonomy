# Taphonomy Development Environment Specification

* **Status:** Initial specification
* **Date:** 2026-08-28
* **Scope:** Local development environment, toolchain, quality gates, dependency policy, and agent-assisted development

---

## 1. Purpose

This document defines the development environment and engineering controls for Taphonomy.

The purpose is to make development:

* reproducible
* reviewable
* deterministic where practical
* safe
* maintainable
* suitable for long-term development

The environment is part of the project's engineering infrastructure.

Changes to this specification must be intentional and documented.

---

# 2. Development Environment

Initial development will occur on:

```text
Host OS:
Windows

Linux environment:
WSL2

Linux distribution:
Ubuntu

Primary development shell:
Linux shell inside WSL2
```

The project must not require a VPS, cloud VM, or remote development environment.

The initial system is local-first.

---

# 3. Repository Location

The working repository is located inside the WSL filesystem.

Expected development location:

```text
~/projects/taphonomy
```

Development should occur from the Linux filesystem rather than through a `/mnt/c/...` working copy unless a specific experiment requires Windows filesystem access.

This reduces filesystem interoperability issues and keeps normal Cargo operations inside the Linux environment.

---

# 4. Source Control

Git is mandatory.

The primary branch is:

```text
main
```

Every meaningful architectural or implementation milestone must be committed.

The working tree should be clean before starting a major milestone.

Changes should be divided into logically coherent commits.

Commit messages should describe the actual change.

Examples:

```text
docs: record initial technology and evidence architecture
build: establish Rust workspace
feat: add read-only evidence source
test: add raw evidence fixtures
```

Large mixed commits containing unrelated documentation, architecture, implementation, and formatting changes should be avoided.

---

# 5. Rust Toolchain

Rust is the primary implementation language.

The project will use the Rust stable toolchain unless a specific technical requirement requires another channel.

The project must pin or otherwise explicitly define its expected Rust toolchain as soon as the first Cargo workspace is created.

A `rust-toolchain.toml` file should be used when the project begins implementation.

The toolchain file should define:

* Rust channel/version
* required components
* required targets, if any

The project must not silently depend on an arbitrary developer's installed Rust version.

---

# 6. Cargo

Cargo is the project build system and dependency manager.

The project must commit:

```text
Cargo.toml
Cargo.lock
```

`Cargo.lock` must remain under version control.

Dependency updates must be intentional.

Automatic dependency upgrades must not be allowed to silently change the project's dependency graph.

---

# 7. Formatting

Rust code must be formatted using:

```text
cargo fmt
```

Formatting is mandatory.

Formatting-only changes should be isolated from functional changes where practical.

The repository should eventually provide a standard command that verifies formatting without modifying files.

Expected verification:

```text
cargo fmt --all -- --check
```

---

# 8. Linting

Clippy will be used for Rust linting.

Expected verification:

```text
cargo clippy --workspace --all-targets --all-features -- -D warnings
```

Warnings should normally be treated as errors.

A lint must not be disabled merely to make the build pass.

Lint exceptions require justification.

---

# 9. Testing

The project must maintain automated tests from the beginning.

The minimum test command is:

```text
cargo test --workspace
```

Tests must be added alongside functionality rather than accumulated later.

Recovery code must have tests for:

* valid input
* truncated input
* malformed input
* boundary conditions
* unexpected offsets
* invalid sizes
* unsupported structures
* corrupted metadata

---

# 10. Test Categories

Taphonomy will eventually distinguish at least:

```text
Unit Tests
Integration Tests
Fixture Tests
Recovery Tests
Regression Tests
Property Tests
Fuzz Tests
```

Not every category needs to exist immediately.

A category should be introduced when the project reaches the point where it provides measurable value.

---

# 11. Evidence Fixtures

Synthetic evidence fixtures are mandatory for recovery development.

Fixtures should be:

* deterministic
* reproducible
* documented
* small enough for development
* version-controlled when practical
* generated by documented procedures

Real personal data must not be committed to the repository.

Real user recovery cases must never become ordinary test fixtures without explicit sanitization and authorization.

---

# 12. Golden Results

Where recovery output is deterministic, expected results may be stored as golden fixtures.

A golden result should document:

* input fixture
* expected behavior
* expected metadata
* expected hashes where appropriate
* expected recovery status

Golden results are regression controls.

Changes to golden results require an explanation.

A test must not be changed merely to match a newly produced incorrect result.

---

# 13. Physical Devices

Physical storage devices must not be required for ordinary development.

Initial development should use disk images and synthetic fixtures.

Physical-device testing is a separate experimental activity.

Before physical-device support is introduced, the project must establish:

* read-only access strategy
* platform-specific behavior
* device identification safeguards
* permission requirements
* write-protection strategy
* failure handling
* operator confirmation requirements

---

# 14. Evidence Integrity

Evidence must be treated as immutable input.

Recovery algorithms must not write to the source evidence.

The architecture must prevent accidental write access wherever practical.

Recovered output must be written to a separate destination.

Where appropriate, evidence should be hashed before analysis and the hash recorded with the analysis session.

---

# 15. Dependency Policy

Dependencies must have a documented reason for inclusion.

Before adding a dependency, consider:

1. Does the standard library already provide the required functionality?
2. Is the dependency actively maintained?
3. Is the dependency widely used or technically credible?
4. What is its license?
5. What are its transitive dependencies?
6. Does it introduce unsafe code?
7. Does it materially increase attack surface?
8. Does it lock Taphonomy into a specific architecture?
9. Can its functionality be isolated behind an internal abstraction?
10. Is the dependency required now, or only useful for a hypothetical future feature?

Dependencies should be added because they solve a demonstrated problem.

---

# 16. License Policy

Taphonomy should prefer permissively licensed dependencies.

Preferred licenses include:

```text
MIT
Apache-2.0
BSD-family licenses
ISC
```

Other licenses require explicit review.

GPL, LGPL, CPL, IPL, AGPL, SSPL, custom, source-available, or otherwise restrictive licenses must not be introduced into the dependency graph without a documented decision.

License compatibility must be evaluated for both direct and relevant transitive dependencies.

---

# 17. Unsafe Rust

`unsafe` Rust is permitted only when technically justified.

Each use of `unsafe` must have:

* a clear reason
* a small scope
* documented safety invariants
* tests covering the relevant behavior
* review of the surrounding assumptions

Unsafe code must not be introduced merely for convenience or speculative performance.

The project should minimize the amount of unsafe code in the trusted computing base.

---

# 18. Binary Parsing Rules

Code parsing external or recovered binary data must assume that input can be:

* truncated
* corrupted
* inconsistent
* maliciously constructed
* internally contradictory
* extremely large
* intentionally designed to trigger pathological behavior

Parsers must validate:

* offsets
* lengths
* integer conversions
* alignment assumptions
* bounds
* recursion depth where applicable
* allocation sizes
* relationships between metadata structures

A parser must fail safely when input cannot be trusted.

---

# 19. Error Handling

Errors must preserve useful diagnostic information.

The system should distinguish, where appropriate:

```text
Invalid Input
Corrupt Evidence
Unsupported Format
Unsupported Feature
I/O Failure
Permission Failure
Internal Error
Validation Failure
```

The project should avoid converting all failures into generic errors such as:

```text
Something went wrong
```

Recovery software must make failures diagnosable.

---

# 20. Logging and Diagnostics

Diagnostics must be useful during local development without exposing recovered user data unnecessarily.

The system must not automatically upload:

* evidence
* recovered files
* filenames
* filesystem metadata
* device identifiers
* personal information

There will be no mandatory telemetry in the initial architecture.

---

# 21. Network Access

The initial recovery engine must not require network connectivity.

Normal recovery operations should function offline.

Dependencies may be downloaded during development through Cargo, but runtime recovery must not depend on an external service.

Future network-dependent functionality requires a separate architectural decision.

---

# 22. Secrets

Secrets must never be committed.

This includes:

* API keys
* tokens
* credentials
* private certificates
* signing keys
* personal access tokens
* device credentials

Local development secrets must be stored outside the repository.

---

# 23. Agent-Assisted Development

Claude Code and other coding agents may be used during development.

Agents must follow:

```text
CLAUDE.md
```

and all applicable project documentation.

Agents must not override:

* safety requirements
* architectural decisions
* security requirements
* testing requirements
* dependency policy
* evidence integrity rules

An agent must not make large architectural changes without documenting the reason.

---

# 24. Agent Change Discipline

Agents should work in small, verifiable steps.

The preferred cycle is:

```text
Understand
    ↓
Plan
    ↓
Change
    ↓
Format
    ↓
Lint
    ↓
Test
    ↓
Inspect diff
    ↓
Propose commit (author commits manually)
```

An agent should not generate large amounts of speculative code before validating the underlying design.

---

# 25. Documentation Requirement

Material engineering decisions must be documented.

Use:

```text
docs/decisions/
```

for architectural decisions.

Use:

```text
docs/development/RESEARCH_LOG.md
```

for research findings.

Use:

```text
docs/development/EXPERIMENTS.md
```

for experiments and their results.

Use:

```text
docs/development/KNOWN_ISSUES.md
```

for known defects and limitations.

Documentation should explain not only what was chosen, but why.

---

# 26. Verification Before Commit

Before a meaningful implementation commit, the following should be run where applicable:

```text
cargo fmt --all -- --check
cargo check --workspace
cargo test --workspace
cargo clippy --workspace --all-targets --all-features -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --document-private-items
git diff --check
```

Not every command is required for documentation-only commits.

The commit message should reflect what was actually verified.

---

# 27. No Premature Infrastructure

The project should not introduce infrastructure before it is needed.

Avoid adding:

* databases
* web servers
* cloud services
* message queues
* container orchestration
* telemetry
* distributed systems
* unnecessary frameworks

unless a demonstrated requirement exists.

The initial system is a local Rust application.

---

# 28. Reproducibility

A developer starting from a clean environment should be able to determine:

* required Rust version
* required system packages
* build commands
* test commands
* lint commands
* fixture generation commands
* development workflow

from repository documentation.

Undocumented machine-specific setup is considered technical debt.

---

# 29. Development Milestone

The first development environment milestone is complete when:

```text
Rust toolchain
      ↓
Cargo workspace
      ↓
minimal source
      ↓
cargo check
      ↓
cargo test
      ↓
cargo fmt
      ↓
cargo clippy
```

all execute successfully.

No recovery functionality is required for this milestone.

---

# 30. Change Control

Changes to this specification should be documented when they materially affect:

* safety
* reproducibility
* dependency management
* toolchain policy
* testing
* evidence integrity
* agent behavior

Small wording corrections do not require a new ADR.

Material architectural changes should use a new ADR.

---

# 31. Current Status

This specification defines the initial development environment.

It does not define the final production deployment environment.

The project will evolve through measured implementation and documented decisions.
